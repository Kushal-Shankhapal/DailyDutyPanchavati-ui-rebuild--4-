# 1. What this project is

This is a Marathi-first digital daily-duty-chart system for:

> **Panchavati Police Station, Nashik City**

The station currently prepares duty charts manually using DOCX, legacy Kruti Dev Marathi fonts, printed pages, photographs and WhatsApp sharing. Staff commonly copy the previous chart and make same-day changes.

The intended system should:

- prepare the next day's chart;
- allow same-day clerk editing;
- preserve staff, duty, leave, closure and charge information;
- eliminate repetitive manual formatting;
- keep finalized charts immutable;
- support amendments as new versions;
- print a clean, compact duty chart;
- retain historical charts for search and reprinting;
- eventually support events, OCR-assisted legacy import, and operational history.

The core rule is:

> **The clerk decides. The software calculates, validates, flags conflicts, preserves history and renders.**

The software must never autonomously select, replace or schedule personnel.

Important findings:

- PaddleOCR plain recognition produced the best Marathi text.
- PP-StructureV3 produced the best layout/table geometry but poor Devanagari recognition.
- Tesseract was much faster but has no table/layout understanding.
- The useful future design is a fusion:
  - StructureV3 for table/cell geometry;
  - Devanagari recognizer for cell text;
  - confidence scores and human review;
  - never automatic DB commit.
- OCR should be asynchronous and local/on-premises, not in the daily authoring request path.
- The source DOCX files use Kruti Dev encoding. Direct text extraction produces Latin-looking gibberish. DOCX needs a Kruti Dev→Unicode transcoder; OCR is more appropriate for rendered PDFs/PNGs.

# Design brief: Compact-v4 direction

## 1. Honest verdict on the current mock

### What the mock gets right

`design/panchavati-compv3.html` is a strong starting point because it already has:

- a chart-like document grammar instead of a dashboard;
- low-noise navy/white/slate palette;
- compact row-based staff display;
- a useful command header;
- a reasonable page-1 hierarchy;
- a good six-chowki matrix direction;
- separate leave, manpower, officer and scan information;
- explicit visual distinctions for `रिक्त`, `बंद` and `बिमा`;
- no dependency on the old six-page visual structure.

### What is not yet good enough

The mock was designed with representative/sample data, so it looks more efficient than it is under the full 10/09 data volume.

Main issues:

1. **Page 1 is overloaded**
   - Sr-PI;
   - officer boxes;
   - day deployment;
   - night deployment;
   - office;
   - court/special desk;
   - several long role groups.

   It becomes vertically excessive once real source rows are inserted.

2. **The officer boxes consume too much vertical space**
   - They are useful as a concept.
   - Their current box treatment creates repeated borders and empty padding.
   - They should become a compact command strip or a tight officer matrix, not dashboard-like cards.

3. **Every block feels boxed**
   - The outer table border;
   - block border;
   - sub-table border;
   - row border;
   - chip border.

   That produces the “double border / clutter / AI-generated admin UI” feeling you dislike.

4. **Page 3 has uneven density**
   - One long leave list can force neighbouring columns to leave large empty areas.
   - The current card/grid approach wastes space when categories have very different lengths.

5. **The mock has a dangerous page-fit illusion**
   - Sample data fits.
   - Real 10/09 data does not fit at the same comfortable scale.
   - We must optimize against maximum realistic source density, not against the sample screenshot.

6. **Page count should not be the optimization target**
   - Four tiny unreadable pages are worse than six well-packed pages.
   - The goal is maximum usable information per area without making Marathi difficult to read.

The new chart should be:

> **A clean command document composed of horizontal bands and disciplined columns — not a collection of cards.**

### Remove from the chart itself

- rounded cards;
- shadows;
- decorative pills;
- unnecessary nested borders;
- large empty card padding;
- dashboard KPI tiles;
- oversized section headers;
- repeated page headers taking excessive height;
- labels repeated in every staff row;
- full names repeated everywhere.

### Keep

- one page frame;
- thin section rules;
- restrained table gridlines;
- clear section bands;
- compact source-faithful grouping;
- text-based state labels;
- small color accents;
- full data available through hover/detail editing.

# 3. Proposed chart grammar

## Outer page

Each printed sheet should have:

1. a compact 1-line identity header;
2. a thin date/status line;
3. two to four horizontal content bands;
4. no card shadow;
5. one consistent page border or no border, not several nested frames.

### Header target

```text
पंचवटी पोलीस ठाणे, नाशिक शहर       दैनिक कर्तव्य तक्ता       दिनांक १०/०९/२०२६ · गुरुवार
```

- 10–12px print title;
- 8–9px metadata;
- lifecycle shown as a small text label, not a large pill;
- header height reduced substantially;
- repeated on each print sheet only because it is operationally useful.

## Section band

Use a narrow section band:

```text
01  दिवसपाळी — ०९:०० ते २१:००                         ८२ कर्मचारी
```

- number optional and very small;
- title left aligned;
- time right aligned;
- one 1px rule below;
- no rounded container;
- count is informational and subtle.

## Row grammar

Every staff row should have a predictable form:

```text
role / duty label        staff display name          time / state
```

Example:

```text
रायटर                    पोहवा ६९२ गुंबाडे             —
                         पोशि ५६९ पवार
बिमा                     पोशि १२४४ महाले              बिमा
                         पोशि २१५७ गुंजाळ
```

Rules:

- role labels use `rowspan`;
- role labels are not repeated for every person;
- staff display name uses compact source form;
- full master name remains available in editor/detail view;
- time is a small right-side value;
- role, name and state remain separate fields;
- no inline explanatory prose unless it is source content;
- no value is truncated;
- two-line wrap is allowed;
- avoid one-word orphan lines.

## Staff display

For dense chart display:

```text
rank + buckle + surname
```

Examples:

```text
पोशि ५४२ आहेर
पोहवा ६९२ गुंबाडे
पोनि सुनिल पवार
```

In the editor/detail panel:

```text
Full name: पोहवा ६९२ अनिल बाळु गुंबाडे
Rank: HC
Buckle: 692
Source/status/history...
```

This gives density without losing identity.

## State display

Use text first, color second.

### `रिक्त`

```text
रिक्त
```

- dashed underline or dashed empty-seat rule;
- amber text;
- no filled pill.

### `बंद`

```text
बंद · चार्ज → मालेगाव स्टँड
```

- one compact state row;
- muted hatch or pale yellow background;
- `बंद` never confused with a vacant assignment.

### `बिमा`

```text
पोशि १२४४ महाले   बिमा
```

- small red text marker;
- no large red pill;
- remains assignment-level only.

# 4. Proposed page/section strategy

This is **not a recreation of the old six-page format**. It is a new logical grouping that may still print to five or six adaptive sheets when the real data requires it.

## Sheet 1 — Command + daytime deployment

### Top band: command strip

Replace large officer cards with a compact command strip:

```text
वरिष्ठ पोलीस निरीक्षक: गजेंद्र पाटील
रायटर: ...
चालक दिवस: ...
चालक रात्र: ...
```

Then a compact officer matrix:

```text
अधिकारी        शाखा/भूमिका       आजची नेमणूक
पोनि ...       क्राईम             उपस्थित
सपोनि ...      तपास              ०९–१४
...
```

This preserves the officer information but avoids four large boxes.

### Main body: three lanes

```text
दिवसपाळी मुख्य ठिकाणे | मोबाईल / DB / लॉकअप | कार्यालयीन / विशेष
```

Why three lanes:

- the existing four equal columns make day/night columns too narrow;
- office/special roles have different density from station deployment;
- the chart should not force unrelated rows into equal-height cards.

Use a continuous table within each lane, not a card.

### Daytime content

Include:

- station leadership;
- station amaldar;
- hazari;
- CCTNS;
- wireless;
- Peter/CR/Delta/DB;
- lockup;
- special desk/office roles that actually belong to daytime.

Do not place all chowki people here if they are shown in the dedicated chowki sheet. Avoid duplicate rendering.

## Sheet 2 — Night deployment + instructions

Night data is structurally different from day data.

Do not force night instructions into fake staff rows.

Use:

```text
रात्रपाळी कर्मचारी lanes        रात्रपाळी सूचना
```

Left side:

- checking officer;
- PSO;
- hazari;
- CCTNS;
- wireless;
- mobile teams;
- DB;
- lockup;
- night special posts.

Right side:

- Good Morning Squad;
- Ramkund patrol;
- statue visits;
- chowki rounds;
- DB instructions;
- app scanning;
- establishment closure instructions.

Instructions should be compact numbered text blocks, not huge bordered cards.

## Sheet 3 — Chowki command matrix

This is the strongest part of the current mock and should remain its own focused sheet.

Use a 3×2 grid:

```text
काटया मारूती | पंचवटी कारंजा | मालेगाव स्टँड
सरदार        | फुलेनगर        | मेरी
```

Each chowki block:

```text
चौकी नाव
प्रभारी / वेळ
दिवसपाळी              रात्रपाळी
staff rows             staff rows
बिमा rows              बिमा rows
मार्शल line            बंद / चार्ज line
```

### Important improvement

Do not put thick borders around each chowki.

Instead:

- use a thin vertical rule between columns;
- use a slightly darker heading underline;
- use a very light background only for the heading row;
- use whitespace between groups;
- use one shared outer grid.

A chowki block should feel like a newspaper column, not a dashboard card.

### Marshal handling

Keep the current data model:

- marshal remains a separate operational post;
- display position may fold into its paired chowki;
- its own closure/charge state remains explicit;
- no BIMA inference.

## Sheet 4 — Leave, other duties, events and notices

This should be a flowing multi-column register, not four independent cards.

Suggested structure:

```text
साप्ताहिक सुट्टी | रजा / सिक | तपास / प्रशिक्षण / प्रतिनियुक्ती | इतर सूचना
```

Use:

- category heading once;
- people beneath it;
- date/time annotations in a narrow secondary column;
- no blank card height matching;
- columns should flow downward independently;
- if one category is longer, it continues naturally beneath the next compatible section rather than leaving empty white space.

For notices:

- use a full-width notice strip below the lists;
- numbered lines;
- no card per notice;
- group by day/night/source scope;
- keep source wording.

For 11/09:

- event/bandobast should appear as an optional annex band or additional adaptive sheet;
- not force Ganpati fields into the ordinary daily chart.

## Sheet 5 — Manpower + change ledger

### Manpower matrix

The matrix should remain table-like because it is genuinely tabular.

Improvements:

- compact two-line column headers;
- freeze/shorten only display labels, never data;
- use hairline grid;
- avoid a large surrounding card;
- show source-entered values exactly;
- clearly mark derived values separately;
- do not “repair” contradictory ME/03 values.

### Change ledger

Put it directly below the matrix with only the required columns:

```text
क्रमांक | बदल / कारण | नोंद
```

Do not leave a giant empty table area if there are no entries. Show:

```text
अचानक बदल नोंद: आज कोणतीही नोंद नाही.
```

and preserve an editor action to add one.

## Sheet 6 — Officer summary + scan schedule + sign-off

### Officer summary

Use a two-column table:

```text
क्र. | अधिकारी | कर्तव्य
```

The current 15-row summary is inherently compact and should not be turned into individual officer boxes.

### Scan schedule

The current hourly scan list should become a time grid:

```text
वेळ       चौकी             कर्मचारी
०९–१०     मेरी             ...
१०–११     मालेगाव         ...
...
```

For screen:

- allow a compact horizontal time grid if wide enough;
- for print, use two side-by-side 6-row tables rather than one tall 12-row table.

Example:

```text
०९–१४                              १५–२१
०९–१० ...                          १५–१६ ...
...
१४–१५ ...                          २०–२१ ...
```

This preserves all 12 rows while reducing vertical waste.

### Sign-off

Keep sign-off as a simple bottom rule and three aligned fields. No card.

Do not hardcode “one logical section equals one physical page.”

Use:

- logical sections in `ChartDocument`;
- content-aware print flow;
- continuation only when necessary;
- repeated compact section headers when a section continues;

### Page-fit rules

For every representative real chart:

- no page-level horizontal overflow;
- no content truncation;
- no row loss;
- no font below the agreed minimum;
- no orphaned section title at page bottom;
- no section forced into a tiny unreadable area;

The target is not “fewest pages.” The target is:

> **Fewest readable sheets that preserve every source fact.**

# 9. Lifecycle and finalization

The UI can make the workflow simple:

```text
DRAFT
  संपादन
  अंतिम करा
```

After finalization:

```text
FINALIZED
  सुधारणा सुरू करा
  प्रिंट
```

But technically:

- finalization creates an immutable snapshot;
- “सुधारणा सुरू करा” creates a new amendment draft;
- the original final version stays unchanged;
- the new draft can be edited and finalized separately.

The status label at the top of each chart sheet can remain:

```text
DRAFT
FINALIZED · आवृत्ती १
सुधारणा मसुदा · आवृत्ती २
```

The persistent application header itself should not carry this chart-specific state.
